# 5W1H 技术分析框架

在用户明确要求 5W1H、章节映射困难，或需要系统检查遗漏时读取本文件。

## 使用方式

先建立知识主干，再做映射：

1. 识别知识单元。
2. 判断每个单元回答哪个问题。
3. 合并重复答案。
4. 决定哪些维度值得成为章节。

不要先创建六个空标题再填充。常见优先级是 `What → Why → How → Where → When → Who`，但实际结构由主题决定。

## What：是什么

目标是建立准确边界：

- 用“对象 + 作用 + 边界”给出一句话定义。
- 说明核心对象、所属类别、它不是什么以及易混淆概念。
- 首次解释专有术语，后文保持名称稳定。
- 不从历史背景开始，也不用例子代替定义。

## Why：为什么

目标是解释问题与设计动机：

`旧问题 → 原方案限制 → 新机制 → 改善`

避免“为了满足复杂业务需求”等无具体约束的背景句。

## How：怎么工作

目标是还原从输入到输出的机制：

- 入口、关键步骤、状态位置、判断组件、触发事件、输出和错误路径。
- 流程使用编号列表；状态变化使用状态机；复杂组件关系可使用 Mermaid；算法可用伪代码。
- 源码和配置只保留足以证明机制或帮助复现的最小片段。

## Where：在哪里

仅当系统位置影响理解时展开：

- 所属层次与请求链路位置。
- 上下游和交互组件。
- 用户态或内核态、控制面或数据面。
- client、server、proxy、controller 或 storage 的职责边界。

## When：什么时候

把场景写成可判断的条件：

- 适用与不适用条件。
- 退化点和前置条件。
- 规模变化后的行为。
- 版本、环境和部署限制。

“广泛用于企业场景”没有决策价值；应说明满足哪些条件时值得使用。

## Who：谁

只在主体关系重要时展开：

- 谁发起、拥有、决策、执行或修改规则。
- Subject、Actor、Owner、Controller 等角色如何区分。
- 权限、控制或责任边界落在谁身上。

认证授权、RBAC、协调机制和控制器等主题通常需要 Who；没有重要主体关系时省略。

## 可选扩展维度

仅在有决策价值时增加：

- **Trade-offs**：能力换来的性能、延迟、一致性、复杂度、安全性或运维代价。
- **Alternatives**：存在真实选择或常见混淆时，比较核心模型、优势、代价和适用条件。
- **Failure Modes**：假设失效、性能退化、易错配置、误判表现及验证方式。
- **Real World**：真实采用方式能解释机制时，说明项目具体如何使用，不罗列项目名称。

用户要求固定六段格式时，允许保留全部标题；对无独立价值的项简短说明不展开，不得编造填充内容。
