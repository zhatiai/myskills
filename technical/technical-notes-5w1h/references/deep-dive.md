# 深入模式与证据处理

用户要求详细原理、面试准备、源码视角，或主题依赖外部资料、版本和证据时读取本文件。

## 深入原理

保留全部 P0 和重要 P1，重点展开：

- 关键数据结构与状态变化。
- 调用流程、控制流或数据流。
- 并发模型、错误路径和失败条件。
- 机制带来的性能、一致性、安全性与复杂度权衡。

“详细”不等于复述全部资料。历史、重复背景和无决策价值的边缘细节仍应删除。

## 面试模式

先输出正常笔记，再按需增加：

- 少量高频问题，覆盖定义、动机、机制、边界和替代方案。
- 自测清单，检查读者能否不用术语解释主题、复述输入到输出的机制、指出至少一个不适用场景。

问答不得机械重复正文，也不追求题库数量。

## 源码视角

只有存在可靠源码依据时才写：

- 入口函数和核心调用链。
- 关键数据结构与状态变化。
- 并发模型、错误路径和相关文件路径。

标明适用的版本、分支或提交。不要凭记忆编造函数名、文件名、实现细节或版本行为。源码细节只在能解释公开行为或关键机制时保留。

## 资料处理

用户提供资料时，以其为主要事实范围，执行：

`识别知识单元 → 去重 → 建立关系 → 5W1H 映射 → 压缩`

不要按原文段落逐段缩写。资料互相冲突时明确指出冲突；有更高可信度来源时说明选择依据，不静默合并成一个结论。

需要外部资料时优先使用：

1. 官方文档。
2. RFC 或标准。
3. 官方源码。
4. 官方设计文档或 Proposal。
5. 高质量技术文章。
6. 社区讨论，仅用于补充实践经验。

版本敏感内容必须标明版本或时间范围，不把旧行为写成永久事实。

## 事实、推论与建议

仅在可能混淆时显式标记：

- **事实**：来源直接支持的内容。
- **推论**：由事实推导但来源未直接表述的结论。
- **建议**：结合约束提出的工程选择。
- **待验证**：证据不足或版本未确认的内容。

结论强度不得超过证据强度。无法验证时应缩小结论，而不是用肯定语气补全缺口。
