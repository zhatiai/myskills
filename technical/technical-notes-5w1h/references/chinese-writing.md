# 中文技术写作

在长文需要统一表达、原始材料重复松散，或草稿存在明显 AI 腔时读取本文件。

## 判断顺序

遵循：

`事实 / 代码 / 标准 / 数据 → 观察 → 归纳 → 结论`

证据不足时降低判断强度，并使用“可能”“推测”或“待验证”。不要先写强结论再寻找支持。

## 句子与术语

- 一句话只承担一个主要判断；背景、原因、转折和建议过多时拆句。
- 一个术语保持一个稳定名称，不为语言变化轮换近义词。
- 用对象、动作、关系、条件、数据和结果替代抽象评价。
- 不用作者感受代替工程判断。例如把“方案很重”改为具体部署、状态和运维成本。

## 删除无信息表达

删除不承载事实的主持句和评价，例如：

- “下面我们来看看”“接下来重点介绍”“最后总结一下”。
- “值得注意的是”“可以看到”“不难发现”。
- “赋能”“闭环”“底座”“灵活”“强大”“高效”“优雅”。

这些词只有在紧接着给出可验证的具体含义时才保留。

## Markdown 结构

- `#` 用于主题，`##` 用于主要知识问题，`###` 用于必要子问题。
- 少用四级及以下标题。
- 并列信息用列表，流程用编号列表，真实比较用表格。
- 仅在结构关系复杂且文字不易说明时使用 Mermaid。
- 少量加粗用于快速定位术语或结论，不把整篇笔记做成视觉装饰。
- 默认不使用 emoji。

## 示例与代码

- 一个概念通常保留一个主要例子。
- 第二个例子只用于说明不同边界；三个以上同类例子默认删除。
- 示例必须解释机制、边界或实际使用，不用于增加篇幅。
- 不大段贴源码。代码只用于证明机制、展示关键调用或帮助复现。
- 不用比喻替代定义和机制解释。

## 常见改写方向

- “这种设计非常灵活”改为它允许哪些对象独立变化，以及减少了什么复制或耦合。
- “该方案性能很高”改为在哪个阶段减少了什么操作、等待或数据移动。
- “这个组件非常重要”改为缺失时哪条链路中断、哪个状态无人维护。
