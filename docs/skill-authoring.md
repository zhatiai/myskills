# Skill 设计与编写规范

本规范只关注如何判断、设计、编写和拆分 Agent Skill。目标是用最少且必要的上下文，为一个可重复任务提供准确、可组合、按需加载的能力。

## 1. 是否需要创建 Skill

适合创建 Skill：

- 存在重复出现的具体任务。
- 任务需要稳定流程、非显然知识、固定质量标准或可靠工具用法。
- 没有额外指导时，模型容易漏步骤、结果不一致或反复需要纠正。
- 输入、期望结果、关键约束和完成标准可以说清楚。
- 能划定明确边界，不会与现有 Skill 大面积重叠。

通常不需要 Skill：

- 一次性偏好或当前对话要求：直接写进提示词。
- 模型已经能可靠完成的普通任务：直接提出请求。
- 纯背景知识：保存为普通文档，需要时检索。
- 只有一条简单规则、没有可复用流程：使用更轻量的持久指令。
- 目标宽泛到“处理所有技术问题”“帮助写作”：先收窄任务。

核心判断：

> 它是否会让一类真实、重复的任务比无 Skill 时更可靠？

没有真实用例或能力缺口时，先用普通提示词完成任务，再从成功方法和失败案例中提炼 Skill，不要为假想问题预写大量规则。

## 2. 先定义职责边界

编写前明确：

- **目标**：用户最终要完成什么。
- **输入**：用户通常会提供什么。
- **结果**：可观察的产物或完成状态是什么。
- **约束**：哪些非显然规则会改变执行决策。
- **正向触发**：哪些真实请求应使用该 Skill。
- **反向边界**：哪些相似请求不应使用。

一个 Skill 应围绕一个连贯目标，而不是围绕宽泛领域收集规则。若名称和 description 无法用一两句话准确说明，通常意味着职责过宽或多个工作流混在一起。

## 3. 拆成多个 Skill，还是拆成子文件

### 拆成多个 Skill

出现以下情况时，优先拆成独立 Skill：

- 用户可以单独请求其中一个能力。
- 各部分有不同触发条件、输入、输出或完成标准。
- 各部分能独立复用，并可能与其他 Skill 组合。
- 各部分使用不同工具、权限或风险边界。
- 总 Skill 的 description 必须堆积大量关键词才能覆盖全部能力。

例如，“研究一个主题”和“把研究结果写成销售邮件”是两个可独立触发、可组合的任务，应拆成两个 Skill。

### 保留一个 Skill，拆成支持文件

满足以下条件时，保留一个 Skill：

- 所有模式共享同一目标和最终产物。
- 差异只是深度、平台、格式、领域分支或特殊操作。
- 各分支通常互斥，或只有少数请求才需要。
- `SKILL.md` 能清楚判断何时进入哪个分支。

例如，“生成技术笔记”是共同目标；源码视角、面试模式、中文写作和正式质量检查只是条件化细节，适合放进同一 Skill 的不同 reference。

## 4. 渐进披露与拆分标准

Skill 按三层披露信息：

1. **`name` 与 `description`**：用于发现，只提供准确触发信息。
2. **`SKILL.md` 正文**：Skill 被选中后加载，保存共同核心与路由。
3. **支持文件**：仅在当前任务需要时读取或执行。

目标不是让整个 Skill 包变小，而是避免每次调用加载无关内容。总内容可以丰富，但入口必须聚焦，分支必须能按需发现。

不要用固定行数决定拆分。100～250 行只能算部分复杂 Skill 的经验区间，不是标准；Anthropic 提到的 5,000 words 是宽松上限建议，也不是目标大小。

出现以下信号时考虑拆分：

- 大量内容只服务少见模式。
- 同一约束在多个章节重复出现。
- 普通请求必须加载大量背景、示例、平台细节或检查表。
- 每增加一个场景都要继续增加顶层章节和禁止规则。
- 核心流程与可选细节难以快速区分。

## 5. `SKILL.md` 应保留什么

`SKILL.md` 是执行入口和路由器，不是完整百科。通常只保留：

- YAML frontmatter。
- 目标或成功状态。
- 必要的适用边界。
- 所有模式共享的原则、约束和主工作流。
- 指向支持文件的条件路由。
- 共同输出要求和完成标准。

每个 Skill 必须有且只有一个 `SKILL.md`，至少包含：

```yaml
---
name: focused-skill
description: 完成什么任务，以及在什么具体请求中使用。
---
```

`name` 使用小写字母、数字和连字符，保持简短稳定，并与目录名一致。

`description` 是主要触发信号：

- 同时说明“做什么”和“什么时候使用”。
- 指向具体任务，不用宽泛领域词吸引无关请求。
- 只在能防止真实误触发时写排除边界。
- 不放完整流程、长示例、营销语言或关键词清单。

正文不要求固定标题。只要另一个 agent 能快速理解共同目标、核心做法、何时读取其他文件以及怎样算完成即可。

## 6. 子文件如何分工

只创建确实会被使用的目录和文件。

| 位置 | 用途 | 不应放入 |
| --- | --- | --- |
| `references/` | 特定模式或平台的流程、领域规则、schema、API 说明、写作规范、检查表和大量示例 | 每次执行都需要的核心规则、可执行脚本 |
| `scripts/` | 重复转换、解析、校验、批处理等更适合确定性执行的逻辑 | 仅供阅读的长篇说明 |
| `assets/` | 最终产物会复制、填充或改造的模板、字体、图片、图标和项目骨架 | 模型需要读取的指令 |

补充规则：

- 每个 reference 围绕一个连贯主题。
- `SKILL.md` 必须说明何时读取或执行每个支持文件。
- 不在入口和 reference 重复维护同一规则。
- 尽量从 `SKILL.md` 一跳到目标文件，避免深层引用链。
- 脚本应明确是直接运行还是作为参考阅读，并实际验证。
- 不为凑齐结构创建空目录、占位文件、重复 README、安装指南或变更日志。
- 只有宿主环境确实需要时才添加 UI 元数据、依赖声明或平台配置。

## 7. 路由必须说明条件

错误：

```markdown
详细资料：
- `references/deep-dive.md`
- `references/writing.md`
- `references/quality-check.md`
```

正确：

```markdown
- 用户要求深入原理时，读取 `references/deep-dive.md`。
- 长文需要统一表达时，读取 `references/writing.md`。
- 产物较长或用于正式交付时，读取 `references/quality-check.md`。
```

普通请求应尽量只依赖 `SKILL.md`。多个条件同时成立时，只读取对应文件，不默认遍历整个 `references/`。

## 8. 避免过度指导

Skill 只补充非显然、任务特有且会改变决策的信息。删除或合并：

- “仔细思考”“保证高质量”“不要写废话”等泛泛提醒。
- 多个章节中语义相同的压缩、去重或质量要求。
- 为所有可能异常预写的猜测性禁止规则。
- 不影响结果的背景介绍和同类示例。
- 模型无需说明也能合理完成的微观步骤。
- 只为形式完整而存在的章节和检查项。

只有在顺序错误会造成实际失败、涉及权限与安全、工具或格式确实脆弱，或真实失败证明需要时，才保留详细步骤和硬约束。

一条规则若不能说明它防止什么具体错误，通常不应成为硬约束。

## 9. 设计与验证流程

1. 收集 2～3 个真实的应触发请求，以及至少一个相似但不应触发的请求。
2. 明确输入、输出、成功标准和已观察到的能力缺口。
3. 检查现有 Skill；能通过小改动复用时不要重复创建。
4. 决定使用一个 Skill、多个可组合 Skill，还是一个 Skill 加条件化支持文件。
5. 先写最小 `SKILL.md`，只在有明确用途时添加其他文件。
6. 检查 description 的触发准确性和所有路由的可发现性。
7. 验证 frontmatter、文件名、链接与脚本，删除 TODO、占位符和未使用资源。
8. 用真实任务验证结果，不以固定标题或措辞作为测试目标。
9. 根据观察到的失败做窄幅修正，不为偶发案例堆叠全局规则。

完成前确认：

- Skill 解决重复且具体的任务。
- 职责边界清楚，不与其他 Skill 大面积重叠。
- `SKILL.md` 只包含共同核心和条件路由。
- 可选内容不会在每次调用时全部加载。
- 每个支持文件都有明确用途和入口。
- 没有把经验行数误写成硬性标准。
- Skill 可与其他 Skill 组合，不假设自己是唯一能力。
