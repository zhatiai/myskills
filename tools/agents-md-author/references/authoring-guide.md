# AGENTS.md 编写指南

本指南用于创建、修改、拆分和审查 Codex 的 `AGENTS.md` 与 `AGENTS.override.md`。目标不是建立一份庞大的项目百科，而是让代理在正确的目录范围内获得少量、长期有效、能改变执行决策的指令。

## 1. 先理解加载模型

Codex 会从项目根目录向当前工作目录逐层查找项目指令。每一层优先选择 `AGENTS.override.md`，否则选择 `AGENTS.md`，再考虑配置的 fallback 文件名；同一目录最多加载一个文件。越靠近当前目录的指令越具体，发生冲突时覆盖更上层的规则。

由此得到四条设计约束：

1. 根目录规则会影响整个仓库，应保持少而稳定。
2. 子目录规则只应描述该子树真正不同的约定。
3. 同目录存在 `AGENTS.override.md` 时，普通 `AGENTS.md` 不会同时生效；不要把 override 当成普通补丁文件。
4. 普通 Markdown 文件不会仅因被放进仓库而自动成为指令。若要按需使用，必须在已加载的 `AGENTS.md` 中写出明确的触发条件和读取路径。

官方行为说明：

- [Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md)
- [Codex prompting guide：Using agents.md](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)

## 2. 先选对载体

不要把所有说明都塞进 `AGENTS.md`。按内容寿命和复用方式选择载体：

| 内容 | 合适载体 |
| --- | --- |
| 整个仓库长期成立的命令、边界、目录约定 | 根 `AGENTS.md` |
| 仅某个子树成立的测试、语言或架构约定 | 子目录 `AGENTS.md` |
| 需要暂时完全替代同目录常规指令 | `AGENTS.override.md` |
| 可跨项目复用、具有多个步骤的工作流 | Skill |
| 只在本次任务成立的要求 | 用户提示词或任务计划 |
| 场景化的长说明、手册或决策表 | 独立文档，由 `AGENTS.md` 按条件路由 |

判断标准是：如果某条内容对该作用域内的大多数后续任务都没有帮助，就不应常驻在该层 `AGENTS.md` 中。

## 3. 调研后再写

写入持久指令前，只读取与目标有关的证据：

- 当前指令链中的 `AGENTS.md` / `AGENTS.override.md`。
- 目标目录及其关键入口文件。
- 实际存在的构建、测试、格式化和生成命令。
- README、配置文件或 CI 中已经执行的约定。
- 用户明确给出的权限边界和维护要求。

不要把尚未验证的命令、临时排障步骤、一次失败经验或个人猜测写成全局规则。若事实仍不确定，先核验；无法核验时，明确标记限制，不要伪装成确定约定。

## 4. 选择最窄合理作用域

把规则放在它真正适用的最高层，但不要高于其有效范围。

示例：

```text
repo/
├── AGENTS.md                  # 全仓库提交、验证和安全边界
├── ios/
│   └── AGENTS.md              # 仅 iOS 的构建与界面规范
└── backend/
    └── AGENTS.md              # 仅后端的迁移与测试命令
```

如果 `ios/` 与根目录没有不同约定，就不要创建 `ios/AGENTS.md`。嵌套层级只有在能减少无关上下文或表达真实差异时才有价值。

修改某个目标文件时，应遵守所有覆盖该文件的上层和同层指令。审查时要同时检查：

- 上下层是否重复同一规则。
- 子层是否无意扩大或取消上层边界。
- 同名规则冲突时，哪个层级实际生效。
- 文件移动后，原作用域是否仍然正确。

## 5. 编写能改变决策的规则

优先记录以下内容：

- 仓库用途、关键边界和真正容易误判的目录职责。
- 已验证的构建、测试、格式化或发布命令，以及何时运行。
- 不明显的生成文件、所有权边界和禁止直接编辑的路径。
- 项目特有的命名、兼容性、架构或验证要求。
- 需要用户确认的外部写操作、发布或破坏性步骤。
- 特定任务应读取的权威项目文档。

一条有效指令通常包含三部分：触发条件、动作、必要边界。

```markdown
- 修改数据库 schema 时，先读取 `docs/database-migrations.md`；只使用仓库现有迁移工具，不手工改写已发布迁移。
```

它优于：

```markdown
- 请谨慎处理数据库。
```

前者会改变具体决策，后者无法验证，也不能指导行动。

## 6. 用条件路由实现渐进披露

当一套详细规则只服务于部分任务时，在 `AGENTS.md` 中保留一行路由，把正文放进独立文件：

```markdown
## 场景路由

- 修改数据库 schema 或迁移时，读取并遵循 `docs/database-migrations.md`。
- 准备生产发布时，读取并遵循 `docs/release-runbook.md`。
```

路由必须满足：

- 触发条件具体，能判断何时读取。
- 路径相对仓库位置清晰且真实存在。
- 被路由文件只负责一个连贯主题。
- 详细规则只维护一份，不在入口和目标文件重复。
- 不形成多层跳转链；通常从 `AGENTS.md` 一跳到目标文档即可。

不要只写：

```markdown
- 相关文档：`docs/guide.md`
```

裸链接没有说明何时需要，也不能确保代理在相关任务中读取它。

## 7. 保持短小但不追逐行数

没有通用的最佳行数。判断是否该拆分时，关注每次自动加载的内容是否都与大多数任务有关。

适合保留在入口中的内容：

- 项目级目标和硬边界。
- 高频且仓库特有的命令。
- 目录组织和验证要求。
- 指向场景化规范的短路由。

适合拆出的内容：

- 某个平台、模块或发布阶段才需要的长流程。
- 大量示例、故障手册、API 说明和背景知识。
- 仅在审计、迁移或特殊交付物中需要的检查表。

OpenAI 当前建议减少臃肿上下文，按任务需要读取资料，并让复杂 Skill 或项目指令采用渐进披露，而不是让每次小改动都加载完整手册：

- [Rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 8. 避免这些反模式

- **重复平台默认行为**：例如泛泛要求“认真思考”“写好代码”“运行合理测试”。
- **全仓库预读**：要求每次任务开始前读取所有架构、数据库和部署文档。
- **没有条件的强制流程**：把只适合发布任务的检查表应用到拼写修复。
- **规则堆叠**：多个章节用不同措辞反复表达同一限制。
- **把 Skill 写进 AGENTS.md**：多步骤、可复用工作流应由 Skill 承担，入口只做路由。
- **把 AGENTS.md 当知识库**：背景说明应进入普通文档，只有影响行动的规则留在指令层。
- **滥用 override**：同目录 override 会取代普通文件，不适合承载局部增量规则。
- **无证据的绝对命令**：不要把未验证偏好提升为 `必须` 或 `禁止`。
- **路径失效**：移动或删除目标文档后仍保留旧路由。
- **权限扩张**：项目指令不能把读取任务自动扩大为提交、推送、发布或外部写入授权。

## 9. 修改策略

新增或编辑时遵循最小改动：

1. 保留现有有效规则和章节风格。
2. 合并语义重复的条目，而不是继续追加近义限制。
3. 只有作用域确实不同才创建嵌套 `AGENTS.md`。
4. 长规则需要拆分时，先创建目标文档，再在入口加入带条件的路由。
5. 未经用户要求，不顺手重写无关规则。
6. 如果现有规则与用户当前请求冲突，说明冲突和优先级，只改动获准范围。

## 10. 完成前检查

逐项确认：

- [ ] 文件位于正确目录，覆盖范围没有过宽或过窄。
- [ ] 内容跨任务长期有效，而不是本次任务的临时说明。
- [ ] 每条规则都会改变执行决策，或提供必要项目事实。
- [ ] 命令、路径、文件名和工具均真实存在。
- [ ] 场景化长内容已拆出，并由明确条件路由。
- [ ] 没有与上层或下层文件产生不必要重复和冲突。
- [ ] 没有误用 `AGENTS.override.md` 导致同目录常规规则失效。
- [ ] 没有扩大外部写入、发布、提交或破坏性操作的授权。
- [ ] 变更说明能指出修改的层级、适用范围和验证方式。

必要时，可在目标目录启动一个只读 Codex 会话，让它总结当前生效的指令和来源，以验证发现顺序与路由是否符合预期。不要用该验证步骤执行项目修改。
